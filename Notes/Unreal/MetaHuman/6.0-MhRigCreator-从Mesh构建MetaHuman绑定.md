## 1. 这个工具解决什么问题

日常拿到的交付物往往只有**一套符合 MetaHuman 官方拓扑的模型**（头部 9 个 LOD0 网格 + 身体网格），没有 DNA。Epic 官方 `MetaHumanForMaya` 插件里的 conform 流程只存在于交互式 UI 中，且[4.6 记录的手工对位](4.6-MetaHuman%E5%85%B3%E8%8A%82%E5%AF%B9%E4%BD%8D.md)需要人肉摆 25 根 `user_defined_joints`。

MhRigCreator 把这条路径脚本化成一条可批处理的流水线：

```
拓扑校验 → 骨骼重定位 → 表情重算 → 输出 DNA → 装配 Maya 绑定（头身骨架合并）
```

**定位要点**：它不重新实现 DNA/RigLogic，而是**复用插件自带的原生库**（`dna` 10.1.4 / `dnacalib2` 5.1.4 / `rdf` 6.5.8 / `frt_api` / `mh_assemble_lib` / `mh_character_assembler`），只把「骨骼该摆到哪」这一步换成自己的多策略几何拟合 —— 那正是官方留给人工的部分。

> ⚠️ 项目明确禁止引入 [OpenRigLogic](5.0-OpenRigLogic%20%E6%98%AF%E4%BB%80%E4%B9%88.md)：它的 `dna` 是 13.2.5，与插件的 10.1.4 冲突（正是 `MetaHumanForMaya.py:dependency_checks()` 警告的场景）。OpenRigLogic 在本项目里只作为格式文档与离线交叉验证参考。

## 3. 核心算法：骨骼定位的 6 级证据强度分层

DNA 的中性骨骼只存**局部平移 + 局部旋转**，「网格变了骨骼该去哪」没有唯一答案。工具按**证据强度**分级叠加，一根骨骼由第一个能定位它的策略接管（`joints/fit.py`）：

| 优先级 | 策略 | 实现 | 依据 |
| --- | --- | --- | --- |
| 0 | 外部硬约束 | `fit.py` `preset_targets` | 头身共享骨骼，由另一侧拟合结果回灌 |
| 1 | 官方顶点映射 | `vertex_map.py` | Epic 自带 `vertex_joint_mapping/*.csv`，surface 直接吸附、volumetric 加固定偏移 |
| 2 | 眼球球心拟合 | `eyeball.py` | 代数球面最小二乘（4x4 正规方程 + 高斯消元） |
| 3 | 链上插值 | `twist_rules.py` | **从原型 DNA 自身反解** `lerp(A, B, w)`，不维护外部规则表 |
| 4 | 蒙皮权重迁移 | `skin_transfer.py` | 骨骼跟着它影响的皮肤走（权重加权位移均值） |
| 5 | 子树相似拟合 | `subtree.py` | 已定位子孙的相似变换（极分解求 R + Umeyama 闭式解求 s） |
| 6 | 随父刚性跟随 | `hierarchy.py` 默认行为 | 兜底。实测头身两侧均已归零 |

### 几个设计上很讲究的点

**只改平移不改旋转。** 与 Epic 一致。DNA behavior 层里每个表情的关节变换都是相对中性姿态的增量，改动中性旋转会让 1673 个表情全部失效。这条约束还带来一个漂亮的副作用：世界↔局部换算只需一次减法 + 一次旋转转置，不涉及矩阵求逆；线性混合蒙皮也退化成加权平移和，`mesh_fill.py` 才能用一行闭式公式补网格。

**自上而下求解。** `JointSkeleton.solve()` 按层级深度排序后逐个换算 —— 父骨骼一动子孙世界位置全变。官方 `utils/dcc.py` 靠 CSV 行序隐含保证这件事，这里改成显式排序，不依赖数据文件顺序。

**子树拟合必须带缩放项。** 早期版本只求旋转（纯刚性 Procrustes），体型缩放场景下系统性偏移。受控实验（把 `thigh_l` 全部子孙放到精确位置、只让该策略反推它）：

| 形变 | 仅旋转 | 旋转 + 缩放 |
| --- | --- | --- |
| 等比 1.04 | 2.0553 cm | **0.0000 cm**（`s` 正确解出 1.04000） |
| 非等比 1.02/1.09/1.05 | 4.6391 cm | **0.6471 cm** |

**没有子孙的骨骼继承最近已定位祖先的变换。** MHB.1 的 `head` 是叶子骨骼（面部骨骼在头部 DNA 里），`neck_02` 唯一子孙就是 `head` —— 整条颈链拿不到样本。改为继承 `spine_05` 的 `(s, R)` 后 `head` 从 1.057 cm 降到 **0.048 cm**。

**绑定锚点自动识别。** 位于世界原点的根骨骼（MHB.1 的 `root`）被排除在所有策略之外 —— 它是地面锚点不是解剖关节，不排除会让子树拟合把整套骨架拖偏 5.09 cm。而 MH.6 头部的根 `spine_04` 在原型里是 `(0, 117.62, 3.28)`，是真会动的解剖关节，必须参与拟合。这条判据是**从数据推导**的（`detect_anchor_joints`），不是硬编码名单。

### 先身体、后头部：一个很有价值的架构决策

头部 DNA 里保留了 27 根身体侧骨骼（`spine_04`~`upperarm_*` 与颈链），而头部 9 个 LOD0 网格几乎覆盖不到肩背。流水线**先拟合身体、再把这 27 根世界位置作为优先级最高的硬约束回灌头部**。

实测收益（同一真值下，`Assets/head.dna` 为真值）：

| 指标 | 无约束 | 有约束 |
| --- | --- | --- |
| 870 根整体平均 | 0.0537 cm | **0.0073 cm** |
| 870 根整体最大 | 3.3761 cm | **0.6969 cm** |
| 靠蒙皮迁移兜底 | 31 根（平均 1.0698 cm） | **11 根（平均 0.0709 cm）** |
| 靠子树拟合兜底 | 9 根（平均 0.9342 cm） | **2 根（平均 0.2386 cm）** |

合法性依据也是实测出来的：配套的一对真值 DNA 里这 27 根骨骼世界位置一致到 **4.6e-5 cm** —— 官方管线本身就满足这个约束。

## 5. 测试设计：三个值得学习的手法

**① 真值 DNA 打分 vs 合成变形打分，各补对方的短板。**
头部用 `Assets/head.dna` 这份 Epic 出品的**另一个角色** DNA 当真值 —— 结构与原型完全一致（870 骨骼/50 网格/8 LOD/782 BS 通道）但几何不同（网格差 2.87 cm、骨骼差 4.01 cm）。骨骼位置由 Epic 管线产出，不是自己造的，这是最有说服力的打分。
身体没有第二份 MHB.1，改用**解析真值**：对模板网格施加已知仿射变形，正确骨骼位置就是同一仿射作用到原骨骼位置的结果。自给自足、能精确定位误差来源，代价是只覆盖仿射形变。

**② 空转护栏。** `MIN_MEANINGFUL_BASELINE_CM = 0.5` + `MIN_IMPROVEMENT_FACTOR = 5.0`：如果「不拟合的基线」本身误差就很小，说明模板与目标太接近、这次打分**没有区分能力**，直接判失败而不是让它蒙混过关。这条护栏能防住「测试一直绿但其实什么都没测」这类最危险的假阳性。

**③ 骨骼归属完整性断言。** `CoverageReport.assert_complete()` 强制「策略定位数 + 随父跟随数 + 锚点数 == 骨骼总数」，`duplicates()` 再核对没有骨骼被两个策略同时记录。870 根骨骼一根都不能悄悄漏掉。

**④ 被数据否掉的方案也留在注释里。** 例如「用一环邻域极分解旋转 volumetric 偏移」看起来很合理（CSV 里的 delta 确实会随局部形状转动），实测**明显更差**（平均 0.54 cm、最大 2.08 cm），于是保留 Epic 原始规则。这类「负结果」记录避免了后人重复踩坑。

## 6. 踩过的坑（工具层面的硬知识）

这些是复用 Epic 插件时最容易静默出错的地方，源码注释里都有实测依据：

**`dna` reader 的生命周期会段错误。** SWIG 包装层用 `__del__` 调 C++ `destroy()`，**被隐式回收的 reader 会让进程崩**：

```python
db = dna_io.read(path).getDBName()      # 崩溃：reader 是临时对象
```

`dna_io` 因此维护一个模块级注册表 `_OPEN: list[(reader, keepalive)]`，把 `(reader, stream)` 登记进去防止隐式回收，用完显式 `release()`（严格「先 reader 后 stream」顺序）或用 `with dna_io.opened(path)`。

**`dna` / `dnacalib2` / `rdf` 不抛异常**，只设全局 `Status` 位。忘记检查会让错误一路静默传播。

**additional assemble script（AAS）有三个版本，只有一个是对的：**

| 路径 | 签名 | 能用吗 |
| --- | --- | --- |
| `mh_expression_editor/res/<rig>/rig_editing/additional_assemble_script.py` | 2 个位置参数 | ✗ lib 用 3 个参数调用，直接报错 |
| `mh_assemble_lib/resources/<rig>/ass_json.py` | 3 个位置参数 | △ 只摆位，**不接 GUI → `CTRL_expressions`**，RigLogic 不会被驱动 |
| `mh_character_assembler/assets/<rig>/ass_json.py` | 3 个位置参数 | ✓ 摆位 + `connect_expressions()`，装配该用这个（MH.6 98KB vs 8KB） |

**`embeddedRL4` 的 `cs` 参数**要写逗号分隔的方向全名（`"left,up,front"`）。写缩写会让插件报 `Unknown direction` 然后**静默**退回默认值。

**批处理下 `cmds.refresh()` 不推动 DG。** 验证形变必须显式 `cmds.dgdirty(allPlugs=True)` + `cmds.dgeval("<mesh>Shape.outMesh")`，否则读到缓存、误判 RigLogic 没生效。

**RigLogic 节点必须在骨骼改名/合并之后建** —— 它靠名字模板连骨骼属性，先建就会连到旧名字上。所以装配时 `ProcessForm.add_rig_logic` 一律为 `False`，改由收尾阶段统一建。

**产出 DNA 比原型小是正常的**（实测 43.4 MB vs 51.8 MB）。表情重算按 `config.json` 的剪枝阈值（corrective blend shape 0.002 cm）丢掉视觉无关的小增量，实测保留约 79% CBS 增量与 99% 关节增量。`export.verify_dna()` 用 `MIN_JOINT_VALUE_RATIO=0.90` / `MIN_BLEND_SHAPE_DELTA_RATIO=0.50` 兜住「behavior 层整体塌掉」这种真故障。

**身体模板可以随便换，但蒙皮权重是唯一风险点。** 流水线覆盖全部体型相关数据（LOD0 全部 30455 顶点、342 根骨骼局部平移、LOD1–3），保留项里中性骨骼旋转逐元素差仅 2.6e-06（与体型无关，注意必须比矩阵而非欧拉角）。但蒙皮权重实测抽样 4351 顶点中 **3708 个（85%）不同**（`pelvis`/`spine_02-04`/各 `*_twist_*` 100% 不同）—— Epic 是按体型分别调权重的，而流水线没有重算蒙皮的手段。**所以要选一份体型接近日常绑定目标的 MHB.1。**

## 7. 代码质量评估与待改进项

### 做得好的地方

- **注释密度与质量都高**：18% 注释率，且几乎每条设计决策都带实测数据与「为什么不那样做」。这在 TA 工具里非常罕见。
- **算法层与 Maya 解耦**：`joints/` 纯 Python，能离线测试。
- **报告导向**：所有 `*Result` / `*Report` 都有 `format()`，人可读、可贴进 issue。
- **隐含契约显式断言**：`_assert_joint_order_matches()` 核对 RDF 与 DNA 的骨骼顺序 —— 这是 `frt_api` 自己也依赖的隐含前提，宁可当场报错也不静默写错 870 根骨骼。
- **失败分级得当**：AAS 是 best-effort（失败只警告），拓扑不一致是硬错误（静默毁绑定）。

### 待改进项（按优先级）

**① 文档内数字已经开始漂移（中优先级）。** 三处对同一批实测数据的记录互相不一致：

| 位置 | 说法 |
| --- | --- |
| `joints/__init__.py:9-14` | 策略只列了 **5 级**（缺"0 外部约束"），且 volumetric「平均 0.27 cm / 基线平均 4.71 cm」 |
| `joints/vertex_map.py:20-22` | 同样是 volumetric 0.27 cm / 基线 4.71 cm |
| `README.md:289` + 实测 | volumetric **0.0568 cm** / 基线 **1.8045 cm** |
| `character.py:12-19` | 共享约束收益「0.0805 → 0.0464 cm」 |
| `README.md:327` + 实测 | 同一收益「0.0537 → 0.0073 cm」 |

README 自己解释了原因（换过一份更接近原型的真值角色，基线从 5.18 降到 1.80 cm），但**模块 docstring 没同步更新**。这类数字散落在 5 处、无单一来源，长期会失真。建议把实测数字集中到 README（或自检脚本输出）一处，模块 docstring 只描述方法与相对结论，不复述绝对数值。

**② `release_all()` 的销毁顺序与 `release()` 不一致（低优先级，已实测无崩溃）。** `release()` 显式按「先 reader 后 keepalive」销毁；而 `release_all()` 里 `_, keepalive = _OPEN.pop()` —— reader 仍被 `_` 引用、stream 先被丢掉，顺序反了。本机实测三轮多 reader 的 `release_all()` 均未崩溃（SWIG 对象持有自己的引用，实际销毁时序被 CPython 引用计数兜住了），但这与模块 docstring 里「反过来会段错误」的说法自相矛盾。既然这条约束被强调过，两个函数应该走同一条销毁路径。

**③ `release_all()` 会摘掉调用方仍在用的 reader（低优先级，设计边界）。** `body_pipeline.build_body()` 的 `finally` 调 `release_all()`，`assemble_character()` 也一样。实测验证：外部先 `dna_io.read()` 的 reader 在别人调 `release_all()` 后会被摘出注册表，之后它就只剩隐式回收路径 —— 也就是模块文档警告的那条崩溃路径。实测该场景没崩，但这是**全局状态被局部函数清空**的典型隐患。建议 `build_body` 只释放自己开的 reader（和 `build_head` 一致），`release_all()` 留给 UI 顶层。

**④ `head_pipeline.py` 完全没有 `Status` 检查（中优先级）。** 全库只有 `body_pipeline.py`（3 处）与 `dna_io.py`（6 处）检查 `Status.isOk()`。而 `dna_io.check_status()` 这个专门为此写的上下文管理器**只在自己的 docstring 里出现过，一次真实调用都没有**。头部流水线里 `rig.set_neutral_joints()` / `set_neutral_mesh()` / `calculateExpressions()` 都是 SWIG 调用 —— 恰恰是「不抛异常只设状态位」的重灾区。目前靠 `verify_dna()` 在末尾兜底，但那是事后发现而非当场定位。

**⑤ 4600 行代码零单元测试框架（中优先级）。** 5 个自检脚本用的是自制 `@check` 装饰器 + 全局 `_results` 列表，脚本级顺序执行、无法只跑单个用例、无参数化、失败后续用例照跑。作为「集成验收」很合适，但 `mathutil` / `twist_rules` / `subtree` 这类纯函数完全可以上 pytest。`pyproject.toml` 里也没有 test 依赖组。

**⑥ CRLF 混入工作区（低优先级）。** 5 个文件（`character.py` / `head_pipeline.py` / `topology.py` / `joints/fit.py` / `tests/check_partial_meshes.py`）在工作区是 CRLF，索引里是 LF，而仓库**没有 `.gitattributes`**。副作用真实存在：这几个文件会被部分工具（含本次分析用的读取工具）判定为二进制而拒绝显示。建议加 `.gitattributes` 固定 `*.py text eol=lf`。

**⑦ 一处 ruff 未消化（很低优先级）。** `uvx ruff check` 报 67 项，其中 `src/` 52 项。绝大多数是可接受的风格取舍（`BLE001` 13 处宽泛 except 多为「日志/探测失败不能影响主流程」的有意设计、`UP035` 17 处 `typing.Sequence` 是 Py3.10 兼容取向）。真正值得修的只有：`joints/vertex_map.py:114` 超行宽 122>120（项目自设 `line-length=120`）、`export.py:99` 的 `ISC004` 隐式字符串拼接、以及 12 处 `RUF100` 无用 `noqa`。

**⑧ 遗留死代码与文档失效引用（很低优先级）。** `joints/skin_transfer.influence_summary()`、`twist_rules.rule_dependency_order()`、`hierarchy.joint_world_positions_from_dna()` / `compare_world_positions()` 均无调用点（前者标注了「用于诊断」尚可，后两者是纯遗留）。另外 README 第 142 行仍在描述 `Assets/SM_MH_test.ma`，但该文件已在 commit `411b7b9`「移除测试资产」中删除；`scene.py:100` 的注释也还引用它。

**⑨ `build/` 有 184 MB 未清理产物（提示）。** 已被 `.gitignore` 覆盖（且写了两遍 `build/`），不入库，但本地占 184 MB，其中 `partial/` 下两个 45 MB 文件是同一份 45967307 字节的重复产物。

## 8. 值得复用到其他项目的模式

1. **证据强度分层 + 第一个命中者接管**：比「一个大而全的算法」更好调试 —— 每根骨骼都能回答「你是被谁定位的、误差多少」。
2. **规则从数据反解，不维护外部表**：`twist_rules` 从原型 DNA 自己投影反解 `lerp` 参数，换 rig 版本自动跟着变。同理 `topology.mesh_roles()` 的网格角色也从映射表推导而非硬编码。
3. **空转护栏**：测试必须先证明「基线足够差」才有资格宣布「拟合足够好」。
4. **导出后读回自检**：DNA 写坏了不报错、只在 UE 里表现成诡异形变 —— 宁可多花两秒读回来核对结构/几何/behavior 三层。
5. **把负结果写进注释**：「试过 X，实测更差，数据如下，所以保留原方案」。
