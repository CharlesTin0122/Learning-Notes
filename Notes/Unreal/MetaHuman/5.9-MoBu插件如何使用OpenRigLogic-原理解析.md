# 5.9 MoBu 插件如何使用 OpenRigLogic —— 原理解析

> 解释 [5.7 C++RigLogic约束插件](5.7-MoBu-C%2B%2BRigLogic%E7%BA%A6%E6%9D%9F%E6%8F%92%E4%BB%B6-OpenReality.md) 项目的核心原理：
> Epic 官方 OpenRigLogic 库在插件中的角色、求解管线、以及"两侧翻译"的集成本质。
> 求解器内部数学详见 [5.0 RigLogic架构设计](5.0-RigLogic%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1-OpenRigLogic.md)。

## 一、OpenRigLogic 是什么

Epic 2026-06 以 MIT 协议开源的 **MetaHuman 绑定运行时**——UE 里 RigLogic 节点、Maya 里
`embeddedRL4.mll` 内部用的**同一套 C++ 库**。两个模块：

| 模块           | 职责                                              |
| ------------ | ----------------------------------------------- |
| **dna**      | 读写 `.dna` 文件（角色绑定数据库：关节层级、中立姿态、控制定义、修形数据、BS 通道） |
| **riglogic** | 求解器：给定控制输入 → 算出所有关节变换增量 + BS 权重                 |

**关键认知：`.dna` 文件 = 数据，RigLogic = 解释器。** MetaHuman 的"绑定"不是节点网络，
而是一个数据文件 + 一个通用求解器。同一个 head.dna 在 UE/Maya/MoBu 三端能逐位一致，
因为大家跑的是同一段求解代码 + 同一份数据。

## 二、求解管线（RigLogic 内部五层）

以 head.dna 为例，`rig->calculate(inst)` 内部依次执行：

```
GUI Controls (174个, 面板控制器语义: CTRL_C_jaw.ty ∈ [-1,1])
   │ ① mapGUIToRawControls —— DNA 内置翻译层
   │    双向轴拆分(jaw.tx=±1→jawLeft/jawRight)、吞咽相位分解、眼睛量程映射
   ▼
Raw Controls (251表情 + 12颈部四元数, 语义: CTRL_expressions.jawOpen ∈ [0,1])
   │ ② PSD 层（Pose Space Deformation, 修正表情）
   │    组合激活: 微笑×张嘴 → McornerPull_Jopen_L = 两者乘积
   │ ③ RBF 层（颈部四元数 → 颈部修形驱动值; body 侧是全身 swing/twist）
   ▼
求解输出
   │ ④ Joints: 稀疏矩阵乘法 → 每关节 9 float 增量 (Δt, Δr, Δs)
   │ ⑤ BlendShapes: 通道权重 [0,1]
   ▼
getJointOutputs() / getBlendShapeOutputs()
```

**输出全部是相对 DNA 中立姿态的增量**——这是集成时最重要的约定，
集成期踩过的坑几乎都源于对"增量"合成方式的理解偏差。

## 三、项目的使用方式

### 3.1 链接方式：静态库直嵌

```
OpenRigLogic 源码 (D:\Code\OpenRigLogic, 5.8分支)
   └─ 编译成 riglogic413_2_5.lib (83MB 静态库)
        ├─ Python 绑定 (dist\py310, pybind11) → Maya/MoBu 脚本原型验证用
        └─ moburiglogic.dll (C++ 约束插件) ← 静态链入, 零外部依赖
```

插件 PE 导入表里**没有** riglogic 动态依赖——求解器整个"焊死"在插件里，部署只拷一个 DLL。

### 3.2 API 使用序列（约束里的实际代码）

```cpp
// 初始化(LoadDna, 一次)
auto* stream = trio::FileStream::create(path, Read, Binary);
auto* reader = dna::BinaryStreamReader::create(stream, dna::DataLayer::All);
reader->read();                              // 解析 .dna → 内存
auto* rig  = rl4::RigLogic::create(reader);  // 编译求解器(矩阵/RBF/PSD 就绪)
auto* inst = rl4::RigInstance::create(rig);  // 每角色一个实例(输入输出缓冲)

// 绑定构建(BuildBindings, 一次): 用 reader 元数据做"名字外交"
reader->getJointName(j)                    // → 匹配场景骨骼
reader->getGUIControlName(g)               // → 匹配面板控制器 "CTRL_C_jaw.ty"
reader->getNeutralJointRotation(j)         // → 预计算校正四元数
rig->getJointVariableAttributeIndices(lod) // 只绑定该 LOD 真正被驱动的关节

// 每帧求值(AnimationNodeNotify, 每 EvaluationID 一次)
inst->setGUIControl(g, 面板位移);   // FaceBoard 模式
rig->mapGUIToRawControls(inst);     // ①层
rig->calculate(inst);               // ②③④⑤层, ~0.1ms
auto jo = inst->getJointOutputs();  // 869关节×9float
auto bs = inst->getBlendShapeOutputs();
```

`RigLogic`（只读，可多角色共享）与 `RigInstance`（每角色状态）分离——多角色天然可行。

### 3.3 两侧的"翻译外交"（项目的真正工作量）

RigLogic 是纯数学库，不认识 MoBu。约束的本质是**双向翻译官**：

**输入侧（MoBu → RigLogic）**：

- 驱动关节 Lcl 欧拉角 → 四元数 → **换算到 DNA 中立坐标系**：
  `q_rel = q(DNA中立)⁻¹ ∘ q(PreRotation) ∘ q(Lcl)`
  （RigLogic 期望"相对绑定姿势的旋转"，MoBu 给的是本地旋转，差一个中立变换）
- 面板控制器：直接读 Lcl Translation 对应轴喂 `setGUIControl`
  （翻译层 DNA 自带——这是 FaceBoard 模式能砍掉自导 mapping json 的原因）

**输出侧（RigLogic → MoBu）**：

| 通道 | 合成方式 | 说明 |
|---|---|---|
| 平移 | `中立 + 增量` 直加 | |
| 旋转 | **看资产惯例二选一** | 身体 FBX 中立烘在 PreRotation → 增量**直写** Lcl；面部 FBX 中立烘在 Lcl（PreRotation≈0）→ **四元数合成** `q最终 = q中立 ∘ q增量` 再转欧拉。直写面部会覆盖中立旋转（踩过的最深的坑） |
| 缩放 | `1 + 增量` | |
| BS | `×100` | MoBu shape 属性量程 0-100 |

## 四、为什么三端能逐位一致

```
              ┌─ UE:   RigLogic 节点(引擎内置)
同一 head.dna ┼─ Maya: embeddedRL4.mll(官方闭源, 同一库的私有编译)
              └─ MoBu: moburiglogic.dll(我们, 开源库静态链入)
```

求解数学 100% 在库内，宿主只做输入输出翻译——只要翻译层正确
（已用弯膝/jawOpen/颈部 RBF 等锚点逐位对照 Maya 官方插件），结果必然一致。

这也是验证策略的理论基础：**离线冒烟（纯库+锚点）就能证掉 90% 的逻辑**，
实机只需验 FBSDK 交互层。

## 五、一句话总结

> 我们没有"实现" MetaHuman 绑定——我们把 Epic 的求解器原样嵌进 MoBu 求值图。
> 项目全部工作量在**两侧翻译**：把 MoBu 的姿态语言（Lcl 欧拉、PreRotation、shape 0-100）
> 翻译成 RigLogic 的语言（相对中立的四元数、0-1 权重），再把结果翻译回来。
> **数学是 Epic 的，外交是我们的。**
