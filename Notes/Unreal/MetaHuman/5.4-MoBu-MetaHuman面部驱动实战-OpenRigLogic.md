## 总体架构

```
表情输入（滑条/脚本/捕捉数据）
    ↓ inst.setRawControl(idx, value)        ← 263 个控制器（CTRL_expressions.*）
RigLogic 求解 rig.calculate(inst)           ← ~0.25ms
    ↓ inst.getJointOutputs()                ← 每关节 9 float 增量（相对中立姿态）
应用层（本笔记核心）
    ↓ SetVector 写 FBModel 局部 TRS          ← ~3.2ms（840 关节）
MoBu 场景骨骼 → 蒙皮网格变形
```

## 三条核心公式（按重要性排序）

### ① 驱动集过滤 —— 只写 RigLogic 声明的关节

```python
var_attrs = rig.getJointVariableAttributeIndices(0)   # LOD0 的可变属性下标
driven_joints = sorted({a // 9 for a in var_attrs})    # 属性 → 关节
```

H10100 的 870 个 DNA 关节中只有 **840 个 FACIAL_\*** 在驱动集内。剩下 29 个（clavicle_pec、spine_04_latissimus、upperarm_correctiveRoot 等）是**肩颈修形关节**——归身体侧 RBF PoseDriver/约束管。

⚠️ **实战教训**：第一版全量写 869 关节，虽然写的是"中立值+零增量"，但等于每帧把修形关节强制钉回中立姿态，与其正常驱动打架 → 用户观察到"脖子和肩膀的修形也在动"。**永远用驱动集圈定写入范围。**

另外跳过根关节（`getJointParentIndex(i) == i`，即 spine_04）：FBX 里它是绑定根、位置在原点附近，DNA 记录的是世界位置（~132cm 高度），不匹配是正常的，不驱动即可。

### ② 平移 = 中立 + 增量

```python
tx = neutral_t[0] + delta_t[0]   # 以此类推 y/z
model.SetVector(FBVector3d(tx, ty, tz), FBModelTransformationType.kModelTranslation, False)
```

### ③ 旋转 = 中立四元数 ∘ 增量四元数（本次最大的坑）

```python
q_final = q_mul(q_neutral[i], euler_to_quat(delta_r))   # XYZ 旋转序
model.SetVector(FBVector3d(*quat_to_euler(q_final)), kModelRotation, False)
```

**为什么不能直接写增量**：该 FBX 的中立旋转烘在 **Lcl Rotation** 里（Pre-Rotation 全零），与 Maya 把 jointOrient 存 Pre-Rotation 的习惯不同。直接用增量覆盖 Rotation 等于清掉所有关节的中立朝向（如下颌的 40° 前倾）→ 整张脸崩坏（"动得诡异"）。

四元数合成正是 Maya 中 `jointOrient ∘ rotate` 的数学等价——Maya 的变换结构替你做了这个乘法，MoBu 要自己做。

验证锚点：H10100 下颌中立 40°，jawOpen=1.0 增量约 22.27° → 合成后 62.27° ✅

**正式工具建议**：初始化时检测骨骼 Pre-Rotation 是否为零，自动选择"合成"或"直写"策略。

## 对齐校验方法

驱动前先校验 FBX 骨架与 DNA 中立值一致（H10100: 869/870 通过，唯一不符是根关节，预期内）：

- 平移：逐分量比较（容差 0.01cm）
- 旋转：**必须用四元数夹角**，欧拉逐分量比较会在 clavicle 等关节误报（欧拉多解：`(123°,82°,113°)` 与 `(-57°,98°,-67°)` 是同一旋转）
- 校验脚本（Maya 版，可移植）：`D:\Code\OpenRigLogic\tools\check_alignment_maya.py` + `dump_dna_neutral.py`

## pyfbsdk 实施要点

| 要点 | 说明 |
|---|---|
| `GetVector/SetVector` | 第 2 参必须传 `FBModelTransformationType.kModelTranslation/kModelRotation` 枚举（int 会报 Boost.Python.ArgumentError）；第 3 参 False = 局部空间 |
| 实时循环 | `FBSystem().OnUIIdle.Add(tick)`，写完调 `Scene.Evaluate()` |
| 关键帧烘焙 | `prop.SetAnimated(True)` → `GetAnimationNode().Nodes[axis].FCurve` → `EditBegin()` / `KeyAdd(FBTime(0,0,0,frame), v)` / `EditEnd()`（批量 KeyAdd 必须包在 EditBegin/End 里，快一个量级） |
| 时间栏 | `FBPlayerControl().LoopStart/LoopStop = FBTime(0,0,0,frame)` |
| 模块遮蔽 | MoBu 无官方 MetaHuman 插件，`import dna/riglogic` 干净无冲突（Maya 则需清缓存） |
| 控制器命名 | `CTRL_expressions.jawOpen`；注意 `eyeCheekRaiseL` 而非 cheekRaiseL——不确定时先列出 ctrl_names 关键词过滤 |

## 实测性能（MoBu 2024, H10100）

| 操作 | 耗时 |
|---|---|
| RigLogic 求解（263 控制器 → 870 关节） | **0.25 ms/帧** |
| SetVector 应用 840 关节 TR | **3.2 ms/帧**（Maya setAttr 的约 1/10） |
| 烘焙 451 帧求解 | 1.4 s |
| 写入 227 万关键帧（840 关节 × 451 帧 × 6 通道） | 3.8 s |

结论：**不做任何优化即可 60fps+ 实时预览**，性能完全不是问题。

## 诊断技巧

- **区分求解错误 vs 应用层错误**：全控制器归零 → calculate → 检查增量。全零 = 求解正确，问题在应用层（本次肩颈问题正是这样定位的）
- DNA 行为层查询：`getRBFSolverCount()` / `getTwistCount()` / `getSwingCount()`。H10100 head.dna 带 1 个颈部 RBF solver（18 个 RBF 控制值），无身体输入时输出为零，不干扰面部；将来做"头颈跟随身体"预览时喂颈椎旋转即可

## BlendShape 同步驱动（2026-07 已完成验证）

- FBX morph target 命名：`head_lod0_mesh__<DNA通道名>`——所有 LOD 网格共用 LOD0 前缀；H10100 每级 LOD 带 858 个 shape，DNA 782 通道全部匹配（0 未命中）
- 写权重：shape 在 MoBu 中是网格模型的 `FBPropertyAnimatableDouble` 属性（`model.PropertyList.Find(shapeName)`），**量程 0–100**，RigLogic 输出 0–1 需 ×100
- 通道下标 = `inst.getBlendShapeOutputs()` 数组下标，初始化时预缓存 `{通道下标: FBProperty}` 映射
- 烘焙策略：全帧求解缓存 → 只给活跃通道（任一帧非零）写 FCurve。实测 451 帧只有 33 个通道活跃，BS 关键帧写入仅 59ms
- **PSD 修正通道自动激活**：微笑+张嘴时 `McornerPull_Jopen_L/R` 等 corrective 通道被 RigLogic 自动算出——组合表情质量与 UE 内一致，这是纯手动映射 BS 方案做不到的
