Python 语言中的“原子操作”（atomic operation）指的是**在多线程环境下，某个操作要么完整执行，要么完全不执行，中间不会被其他线程打断或看到半成品状态**的操作。

Python 由于有 GIL（Global Interpreter Lock，全局解释器锁）的存在，使得很多看起来“不是原子”的操作，在 CPython（官方实现）中实际上是原子的。这也是很多人对 Python 原子性产生困惑的根源。

### 1. 由于 GIL 保证原子性的常见操作（CPython 中）

### 真正原子的操作（无需加锁，多线程 100% 安全）

|序号|操作（纯 Python 代码）|适用对象类型|说明（为什么原子）|
|---|---|---|---|
|1|局部变量的读取和赋值 a = 1; b = a|任何不可变对象（int、str、tuple、frozenset 等）|局部变量在当前线程的栈帧里，读写都在同一条字节码中完成，几乎不可能被打断|
|2|局部变量 i += 1、i -= 1 等增强赋值|仅限 int、float 等内置不可变类型|字节码是单条 INPLACE_ADD，整个读-改-写在一条指令内完成（局部变量特例）|
|3|list.append(item)|list|CPython 实现中 append 是单条字节码 + C 函数内部不释放 GIL|
|4|list.pop()（不带参数，从尾部弹出）|list|同上|
|5|deque.append(item) / deque.appendleft(item)|collections.deque|C 实现，两端操作不释放 GIL|
|6|deque.pop() / deque.popleft()|collections.deque|同上|
|7|dict[key] = value（新建或覆盖）|dict|单条 STORE_SUBSCR 字节码 + C 实现不释放 GIL|
|8|del dict[key]|dict|单条 DELETE_SUBSCR|
|9|set.add(item) / set.discard(item) / set.remove()|set|C 实现不释放 GIL|
|10|queue.Queue.put(item) / queue.Queue.get()|queue.Queue|内部已经加了锁，是官方唯一声明线程安全的容器|
|11|queue.SimpleQueue.put/get（Python 3.7+）|queue.SimpleQueue|无锁实现，但官方保证线程安全|
|12|threading.Event.set/clear/is_set/wait|threading.Event|内部使用条件变量 + 锁|

### 看起来像原子、但实际上不是原子的常见陷阱（必须加锁）

|操作|为什么不是原子|典型丢失次数（2线程各100万次）|
|---|---|---|
|全局变量 g += 1|LOAD_GLOBAL → INPLACE_ADD → STORE_GLOBAL 三步|丢失 10～50 万|
|lst[i] += 1、lst[i] = lst[i] + 1|索引加载 + 计算 + 索引存储，三条字节码|丢失严重|
|对象属性 obj.x += 1|LOAD_ATTR → INPLACE_ADD → STORE_ATTR|丢失严重|
|counter[0] += 1（用列表第一个元素当计数器）|同样是三步操作|很多人中招|
|dict[key] += 1（先读再写）|字典取值 + 计算 + 写回|丢失严重|
|var = var + 1（即使 var 是全局 int）|完全等价于三步操作|丢失严重|

### 真正无锁原子操作（CAS）—— 推荐用于高性能计数

### 3. 真正需要锁来保证原子性的常见场景

尽管 GIL 帮了很大忙，但以下情况仍然需要显式加锁：

```python
# 情况1：涉及多次字节码操作
counter += 1                    # 如果 counter 是自定义对象
mylist[i] = mylist[i] + 1

# 情况2：需要多条语句一起原子执行（逻辑原子性）
if item not in seen:
    seen.add(item)
    result.append(item)

# 情况3：使用 PyPy、Jython、IronPython（无 GIL 或 GIL 行为不同）
# 情况4：与 C 扩展交互，可能释放 GIL
import numpy as np
np_array[...] = ...             # 可能释放 GIL

# 情况5：进程间共享数据（multiprocessing）
```

### 4. 常用的原子操作工具

| 工具                         | 用途                                   | 是否真正线程安全 |
|------------------------------|----------------------------------------|------------------|
| `threading.Lock()`           | 最常用互斥锁                            | 是               |
| `threading.RLock()`          | 可重入锁                               | 是               |
| `threading.Event()/Condition()` | 线程同步                              | 是               |
| `queue.Queue`                | 线程安全队列（内部用了锁）              | 是               |
| `collections.deque`          | 仅两端操作在 CPython 中原子，不保证复合操作 | 部分             |
| `atomic` 第三方库（如 `atomics`） | 提供真正的 CAS 操作                | 是               |
| `concurrent.futures`        | 线程/进程池                            | 是               |

### 5. 真正的无锁原子操作（需要第三方或自己写 C 扩展）

Python 标准库没有提供 CAS（compare-and-swap）原语，但可以通过以下方式实现：

```python
# 使用第三方库
import atomics

atomic_counter = atomics.atomic(width=4, atype=atomics.int)
atomic_counter.fetch_add(1)   # 真正无锁原子递增

# 或 Python 3.11+ 的 multiprocessing.shared_memory（进程间）
```

### 总结：Python 原子操作一览表（CPython）

| 操作场景                       | 是否原子 | 推荐保护方式                 |
|--------------------------------|----------|------------------------------|
| 简单变量读写、+=1（int）       | 是       | 无需锁                       |
| list.append/pop                | 是       | 无需锁（仅单操作）           |
| dict[key] = value              | 是       | 无需锁                       |
| i += 1（自定义对象）           | 否       | 用 Lock                      |
| 多步逻辑组合操作               | 否       | 用 Lock 或队列               |
| 与释放 GIL 的 C 扩展交互       | 否       | 用 Lock                      |
| PyPy / 无 GIL 环境             | 否       | 必须用锁                     |

**经验法则**：
- 在 CPython + 纯 Python + 简单内置类型时，你可以“偷懒”不加锁，很多操作天然原子。
- 一旦涉及自定义对象、列表切片赋值、复杂表达式、I/O、numpy 等，**必须加锁**。
- 写并发代码时，**永远不要依赖 GIL 保证原子性**，养成好习惯用 Lock 或 Queue。

这样写出来的代码才能在 PyPy、未来可能移除/优化 GIL 的 CPython、以及多进程环境中正常工作。
