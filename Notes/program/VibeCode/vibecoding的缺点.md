# 我们如何阻止氛围编码？

2026年7月24日

当Claude Code在2025年12月底附近迅速走红时，大量软件开发人员迅速转向在他们的主要开发工作流中使用编码代理。

创造了"氛围编码"一词的Andrej Karpathy在2026年3月的No Priors播客中表示：

> 我想我可能从12月以来就没打过一行代码了，基本上就是这样，这是一个极其巨大的变化。我不认为一个普通人真的意识到这发生了或者它有多么戏剧性。

我相信他。很多人说这只是营销或炒作，但作为一个自去年以来就没写过一行代码的人，我认为他在这里是诚实的。现在，这是好是坏取决于你的观点，但毫无疑问，我们已经进入了软件工程的新时代。

尽管代理被迅速采用，但从业者和观察他们输出的人之间普遍存在焦虑：这波垃圾内容的浪潮何时才能结束？我们是在为了方便而自我毁灭吗？我们如何阻止这一切？

## 代码之上的意图

UML共同创造者Grady Booch实际上[主张](https://www.youtube.com/watch?v=OfMAtaocvJw)我们正处于软件工程的第三个黄金时代：

- 第一个时代从1940年代末到1970年代，是算法时代。高级语言和编译器抽象化了机器。
- 第二个时代从1970年代到2000年代，是面向对象抽象时代。
- 第三个时代从2000年左右开始，是系统时代：库、平台和API抽象化了整个子系统。

Booch 谨慎地指出，这第三个时代并非由人工智能开启，只是被它加速了。但他也将人工智能编码智能体比作 Grace Hopper 时代编译器的出现，而这正是这里最重要的比较。编译器抽象化了机器。智能体抽象化了代码本身。

我们现在第一次能够直接从意图生成代码。缺乏这种能力正是导致模型驱动开发在过去失败的原因（对 UML 的看法因人而异，但也许现在是我们考虑以某种形式重新引入 MDD 的时候了。）

实际上，当我们在抽象层次上向意图靠近时，我们会失去许多使代码工作成为可靠过程的工具和方法。如果我们能够适应这种转变，我相信这不仅可能加快开发速度，而且可能大大提高软件解决方案的质量。

不过现在的问题是，我们陷入了"感觉编程赌场"。每个人，甚至他们的祖母都在疯狂地编写代码，就像没有明天一样，拉动把手，听天由命。

## 问题所在

直觉式编码几乎普遍被认为存在以下问题：
(a) 对个人理解解决方案和架构有害
(b) 由于提示词规范不足、自然语言接口信息丢失以及代码生成的非确定性特征，导致其不可靠。

当你在进行"氛围编程"时：

- 你开始无法理解自己所处理的代码库。建立的心智模型变得模糊不清，主要依赖于你作为程序员的以往经验。
    - 你会失去对死代码/冗余代码和存根的认识。
    - 你会失去对已实现内容及其原因的追踪。
    - 你无法向他人解释架构，也无法推理潜在问题。
- 在批准计划之前，你几乎无法看到将要发生什么变化。是的，代理通常会写一篇简短的文章解释它将要做什么，但这是有限的。
    - 它不会显示影响范围。
    - 它不会告诉你它只会部分实现某些内容，或者它遗漏了你认为显而易见的关键内容。
    - 即使确实如此，你也可能无法发现，因为这些计划没有可学习的结构。

这是一种黑箱效应，它会逐渐侵蚀你的工作流程，使你作为软件工程师的严谨性下降，最终导致你盲目推送代码提交并导致生产环境宕机。

即使你不这样滥用编码代理，更倾向于手动编程，也很难否认这可能是软件工程的大势所趋。我们可以看到许多工程师已经将编码代理纳入他们的核心工作流程，许多10倍效率的开发者正在尝试用它们创建自主循环，仿佛控制和决策只是对真正目标的干扰：最大化令牌生成。

无论如何，归根结底就是信任问题；你无法相信自己对代码库的理解，也无法相信代理程序是否按照你的意愿行动。

## 解决方案还不成熟

我们都明白这是个问题——但有什么可能的解决方案呢？虽然这个话题讨论得很多，但我认为迄今为止提出的任何方案都远非令人信服。

首先，我们需要就我们究竟想要做什么达成共识：我们希望尽可能地减少对编码代理输出的信任需求。

为了支持这一点，我们希望：

1. **代理能够可靠地执行我们的要求。**理想情况下，应该是确定性的——这可能无法实现，但这是一个很好的目标。
2. **能够审计和跟踪它对我们代码库所做的更改。**最好是不需要必然阅读代码。
3. **为了将摩擦降到最低。**氛围编码之所以胜出，是因为它是阻力最小的路径，我们需要接受这一点，并让有纪律的路径成为容易的选择。

现有的解决方案都没有充分解决这三个问题。其中大多数依赖于，或者干脆_就是_某种形式的提示工程，这_不_同于意图蒸馏(#1。)

### Markdown规范

许多我交谈过的工程师会说出类似这样的话：

> 好吧，我使用markdown规范来协调一个代理管道来审查它们，将其实现为代码，然后管理和更新它们，它会检查一致性，对比现有代码库，标记任何冲突之处，然后交给实现部分，完成后它会循环回来更新规范，这样文档和代码就永远不会偏离，所以markdown才是真正的信息源，其他一切都围绕着保持同步运转...

当我的眼神开始呆滞时，我忍不住在想：

- 你有针对这些规范的系统或结构化格式吗？
- 你怎么知道规范的哪些部分实际上已经实现了？
- 你怎么知道代码做的事情没有超出规范之外？
- 什么是代理管道？你必须不断提醒它你的规范存在吗？
- 我为什么不直接提示代理呢？

由此衍生出了很多问题，通常这些问题的答案都非常模糊——在这一点上，这看起来就像是一种个人工作流优化，没有任何可验证的影响。不管他们在做什么，对他们来说感觉"严谨"，仅此而已。

Addy Osmani在2026年2月的文章《如何为AI代理编写好的规范》很好地说明了这一点。

这不是模糊，确切地说是密集。五项原则、六部分格式、对2500个配置文件的研究、每个你听说过的工具都被提及。看起来像是一个系统。然后你意识到整篇文章只是在描述代理环境中的提示工程。

我们不能认真地称之为规范驱动开发，因为规范不是"事实来源"，而是一个指导性提示。没有强制机制，甚至没有调和机制，除了问代理"代码是否遵循规范？"——而AI可以任意解释这个问题，因为没有共享的语法！

从根本上讲，markdown规范没有解决我们对代理的信任缺乏问题，而且它们管理起来直接很烦人。它们必须变得清晰结构化，并放在更大的系统中才能有用。

### 技能

这些本质上是你根据任务有条件地注入的上下文/指令。虽然它们可能有用，但它们仍然完全依赖代理的遵循，这在完全相同的方式上对我们的需求失败了——即使它们在实现上不那么麻烦。

有趣的是，它们也往往是讨厌的冗余内容，比如这个来自gstack的[巨大的"QA"技能](https://github.com/garrytan/gstack/blob/main/qa/SKILL.md)。

我很确定，用"找出并修复bug吧"这样的提示词，对大多数Agent来说效果会一样好（甚至更好？）。

技能充其量只是补充，就像提示词工程一样。

### [Spec Kit](https://github.com/github/spec-kit) & [OpenSpec](https://github.com/Fission-AI/openspec)等。

Spec Kit是一个markdown模板目录，CLI会将其放入你的项目中。你需要按顺序运行六个命令：specify → clarify → plan → tasks → analyze → implement。

在幕后，Agent被引导按照模板定义所有内容，然后将输出保留作为后续提示的上下文。

这_几乎_是个开始，因为它试图对即兴编码应用某种流程，并为编码Agent定义了一个松散的结构。关键词是"松散"，问题在于开发者驱动整个过程——从一个命令变成了六个——但仍然无法真正**看到**任何东西。

OpenSpec是同一理念的更轻量级版本：explore → propose → apply → archive，而不是六命令管道，用纯markdown的WHEN/THEN场景代替Kiro的EARS。它做了相同的赌注，以相同的方式失败：你驱动流程，Agent给自己的作业打分，但没有什么机制来检查规范与代码的一致性。

这些项目有几十个，它们基本上都是一样的。

### [Kiro](https://kiro.dev/)

通过钩子函数引导代理使用带有EARS需求的markdown规范，以系统化功能开发。

如果你不知道什么是EARS（简易需求语法方法），这里有几个例子展示自然语言需求与EARS需求的区别：

|自然语言|EARS|
|---|---|
|如果用户闲置一段时间，出于安全考虑，应将其登出。|当用户会话闲置15分钟后，系统应终止该会话并将用户重定向到登录页面。|
|优雅地处理支付失败。|如果支付尝试失败，系统应保留购物车内容并显示失败原因。|

EARS在这里的应用很有意思，因为它通过以比纯文本更加结构化的方式来表述需求，对代理和开发人员都很有帮助。当你在处理意图时，使用非结构化的文本会很快让你感到困惑；你无法像扫描代码那样扫描它。EARS有助于解决这个问题。

实现钩子也是个不错的办法，它能强制代理对触发器做出反应，并明确地遵循其流程的步骤。虽然不是确定性的，但这提供了结构。

遗憾的是，Kiro 在两个方面存在问题：

- 功能规范会不断累积，而不是组合；因此没有可审计的图。
- 需求永远无法与已发布的代码相协调；它建立了法庭，却从未进行过审判。

### 测试驱动开发

测试的名称是对意图的描述；是业务或流程需求，必须由代码来满足，用自然语言编写。测试本身是与实际代码的连接点，希望能证明代码与所述意图相符。从这个意义上讲，更高级别的测试甚至可以充当功能依赖图的作用。

终于有了某种确定性执行的样子。这实际上能有所帮助！

然而，开发者通常会让代理写测试，因为这样更容易，但这重新引入了我们试图解决的相同问题。

另一种方法是手动编写测试，但这样你就必须了解代码的实现——而且你必须写代码，我认为如果我们谈论的是抽象化代码，这是个问题。我不是说自己写测试是错误的，但这篇文章是关于如何具体修复"氛围编程"的。作为编程代理爱好者，我们更倾向于停留在意图层面而不是实现层面。

> _旁注：_CodeSpeak——下面会详细介绍——最近遇到了这个确切的问题：最初的想法是开发者会手动编写规范文件，但大多数alpha测试者让他们的代理来做。他们后来改变了策略，转而从自然语言提示中自动提取结构化意图。

所以，我们必须回到原点：TDD解决了部分问题，但前提是我们能够限制代理编写测试的方式，或者以确定性的方式生成测试。

## 拼图落位

之前的解决方案不足之处在于它们没有解决核心问题：信任。

是的，它们试图更好地使代理与我们的意图保持一致。它们试图给代理提供操作程序。它们甚至有一些基本的变更历史记录概念，或者收紧约束（如使用钩子）。

但它仍然是一个提示界面——附加了仪式作为纪律——以及阅读散文或代码。它们无法完整展示你正在进行的工作。它们不能强制代理实现你定义的内容，甚至不能强制实现代理声称已实现的内容。它们没有提供开发者和代理都同意的共享表面。

而且解决这个问题确实很困难。很能说明问题的是，[Tessl](https://tessl.io/)——曾以规范驱动开发的承诺融资1.25亿美元——已经悄悄地从向开发者推销SDD转向了"技能即代码"的理念。有点尴尬吧？

幸运的是，这个领域仍然很年轻且在积极实验，一些方法正开始汇聚到真正有效的解决方案上。

以下两个项目（免责声明：其中一个是我的）我认为是朝着正确方向发展的项目。

_仅供参考，这些是我实际了解的唯一专注于信任问题的项目，但如果还有其他项目，我很乐意听说。_

### [CodeSpeak](https://codespeak.dev/)

由Kotlin的创造者Andrey Breslav创办。

CodeSpeak的理念是信任可以被编译掉：你编写简洁的markdown规范，将其组织成相互导入的模块，然后`codespeak build`将其编译成可工作的代码——Python、Go或TypeScript，你实际上不需要审查。该工具链认真对待"编译器"的框架概念：规范在构建前会被验证一致性，测试在构建后运行，而且`codespeak takeover`甚至可以从现有代码库反向生成规范。

自从我之前提到的那个转折点以来，他们还在上面构建了一个需求层：与你的代理的对话被提炼成结构化的需求，映射到实现它们的代码文件，当变更偏离时会被标记。他们仍在致力于规范化规范语言本身，目标是实现确定性或接近确定性的构建。

### [Scryer](https://github.com/aklos/scryer)

过去六个月里，我一直在开发这个工具，并不断迭代以适应我自己的开发工作流程。

Scryer 采取相反的方式：对代理的信任是不可约的，因此应该尽可能便宜地使用。这是编码代理的模型驱动开发。你和你的代理共享系统的模型：一个 C4 风格的层级结构，其中每个节点用简短的、与语言无关的声明说明其职责，并映射到实现它们的源代码行和证明它们的测试。代理通过 MCP 读写模型；你可以像浏览维基风格的页面和图表一样浏览它，而不是阅读代码。

模型引领；代码跟随。你规划一项变更，该计划以 git 风格的差异形式展示在整个模型上。这就是你的影响范围。其下是一个确定性可观测层，报告已构建的内容与计划内容、哪些声明是有锚点和测试支持的，以及自上次协调以来代码与模型的偏离情况。

## 没有退路

现代软件开发大多就是反复实现相同的模式，使用标准解决方案，以及混搭各种算法。这正是大语言模型擅长的领域——它们在这方面比我们做得更好，说实话，我们为什么还要手动做这些呢？这样做只会导致职业倦怠和愤世嫉俗。

手工编写代码在定制化和新颖复杂的工作中将始终存在。希望许多开发者能够慢慢重新发现对编程的热爱，当他们能够将其应用于真正感兴趣且具有挑战性的问题时。至于其他一切工作，我们应该尽力使编码代理尽可能可靠。

也许我们会继续以飞行员的身份为代理服务，或者自主代理很快就会完成大部分工作。无论哪种情况，它们都需要一个规范——而装扮成流程的提示词仪式是不够的。我们需要超越当前那些半吊子的解决方案，转向真正为此而构建的工具：将意图作为一等公民，并根据代码进行验证。

我们无法回到没有编码代理和氛围编程的世界，但我们可以操纵老虎机，离开赌场。
