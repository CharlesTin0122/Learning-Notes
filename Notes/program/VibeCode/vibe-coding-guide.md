## 一、什么是 Vibe Coding

**Vibe Coding(氛围编程)** 是一种以**自然语言意图**为主导、由 **AI 编程助手生成大部分代码**、人类专注于**描述需求、审阅结果和把控方向**的开发方式。这个词由 Andrej Karpathy 在 2025 年初提出,核心特征是:

- 你**主要用自然语言**描述「想要什么」,而不是逐行手写「怎么做」。
- AI 负责把意图翻译成可运行的代码。
- 你通过**不断对话、运行、反馈**来迭代,而不是一开始就追求完美设计。
- 你的角色从「码字员」转变为「**导演 / 审阅者 / 决策者**」。

> ⚠️ **重要区分**:Vibe Coding ≠ 不看代码就上线。
> 真正可靠的 Vibe Coding 是「**AI 写、你审、共同迭代**」。把 AI 生成的代码当作初稿,而不是终稿。

```
npm i -g opencode-ai@latest
npm i -g @anthropic-ai/claude-code@latest
npm i -g @openai/codex@latest
```

## 二、核心理念与心态

| 传统编程心态 | Vibe Coding 心态 |
|------------|-----------------|
| 先想清楚架构再动手 | 先跑起来,再迭代收敛 |
| 我来写每一行 | 我来描述意图、审阅产出 |
| 代码是产出物 | **可运行的行为** 才是产出物 |
| 怕改、怕重写 | 拥抱快速重写与丢弃 |
| 一次写对 | 多轮对话逼近正确 |

**关键心态转变:**

1. **意图优先**:先把「要解决什么问题、成功标准是什么」说清楚,比纠结实现细节更重要。
2. **快速验证**:让代码尽快跑起来,用运行结果代替纸上推演。
3. **保持掌控**:你始终是负责人。AI 是高效的初级工程师,而不是不需要监督的黑盒。
4. **小步快跑**:每次只让 AI 做一件可验证的事,而不是「帮我写完整个系统」。

## 三、适用与不适用的场景

### ✅ 非常适合 Vibe Coding

- 原型(Prototype)、概念验证(POC)、一次性脚本。
- 工具类脚本(如批处理、资产导入导出、数据清洗)。
- 探索性开发:你对最终方案还不确定,需要快速试几个方向。
- 你不熟悉的语言/框架/API 的「上手」阶段。
- 重复性强、模板化的代码。

### ⚠️ 需要谨慎 / 加强审阅

- 生产环境的核心业务逻辑。
- 涉及**安全、权限、支付、隐私**的代码。
- 性能敏感的模块(如顶点形变、自定义 deformer、大规模资产批处理)。
- 会**不可逆地修改文件/资产/数据库**的操作。
- 需要长期维护、多人协作的核心代码库。

> 经验法则:**越是难以回滚、影响面越大的代码,越要降低对 AI 产出的信任度,加强人工审阅与测试。**

## 四、核心方法论

### 1. 意图 → 生成 → 验证 → 反馈(IGVF 循环)

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│ 意图     │ →  │ 生成     │ →  │ 验证     │ →  │ 反馈     │
│ Intent  │    │Generate │    │ Verify  │    │Feedback │
└─────────┘    └─────────┘    └─────────┘    └────┬────┘
     ▲                                            │
     └────────────────────────────────────────────┘
                    (循环迭代)
```

- **意图**:清晰描述你要什么 + 成功标准。
- **生成**:让 AI 产出代码。
- **验证**:**立刻运行**,看真实结果(而非相信 AI 的「应该可以了」)。
- **反馈**:把错误信息、不符合预期的行为反馈给 AI,继续迭代。

### 2. 小颗粒度原则

不要说「帮我做一个完整的角色绑定工具」,而要拆成:
- 「先写一个函数:输入骨骼列表,创建对应的 FK 控制器」
- 验证通过后 →「再加上控制器的层级与命名规范」
- 再 →「加上颜色和锁定不需要的通道」

每一步都可独立运行、独立验证。

### 3. 让 AI 解释,而不只是生成

要求 AI:
- 说明它的实现思路和假设。
- 指出潜在的边界情况和风险。
- 标注哪些地方它不确定。

这能帮你在审阅时抓住关键点。

## 五、标准工作流程(步骤)

### 步骤 0:准备环境

- 选好 AI 工具(Claude Code / Cursor / Copilot 等)。
- **确保有版本控制(Git)** —— 这是 Vibe Coding 的安全网,让你能随时回滚。
- 准备好可以快速运行/验证的环境(如 Maya、UE、本地 Python 环境)。


### 步骤 1:确认需求（PlanMode）

清晰地告诉 AI:
- **目标**:我要实现什么。
- **输入**:技术栈、运行环境、已有代码、约束条件。
- **输出**:需求文档
- **步骤**：编写需求文档的步骤

```
目标：请为我实现一个fc模拟器，可以玩fc游戏。
输入：请使用Python语言，在Windows11环境下运行，当前目录是一个uv管理的python工程，ROM目录下有超级玛丽游戏的镜像。
输出：请为我编写一个需求文档proposal.md
步骤：我不了解任何fc模拟器的知识。请用提问的方式帮我确认需求。
```

### 步骤 2:让 AI 生成计划
- 开发日志文件
- 开发文档文件
- CLAUDE.md文件
```
请根据需求文档proposal.md规划开发步骤,不要一口气做太多,让项目稳定安全有效的推进。
创建dev_docs文件夹,放入项目开发相关的开发需求、技术、设计规范,执行步骤等等具体标准md文件以及记录完成开发事项和待办事项
在你的CLAUDE.md文件中添加指引各项标准文件路径以及工作说明。
在划分模块时尽量保持模块的独立，方便独立测试。
有不明确的地方请向我提问。
```

> 💡 把项目规范(命名、语言、技术栈偏好)固化到 `CLAUDE.md` / 规则文件中,AI 每次都会遵守,避免重复说明。

### 步骤 3:让 AI 生成初稿

- 先要一个**最小可运行版本**,不要一上来追求功能完整。
- 复杂任务先让 AI **给出方案/计划**,你确认后再生成代码。

### 步骤 4:运行与验证(最关键)

- **亲自运行**,看实际输出。
- 对脚本类任务:遵循「查询当前状态 → 执行 → 验证结果」的流程。
- 不要因为代码「看起来对」就跳过运行。

### 步骤 5:反馈与迭代

- 把报错信息、不符合预期的现象**原样**贴给 AI。
- 一次只聚焦一个问题,避免同时改多处导致混乱。

### 步骤 6:审阅与理解

- **逐段读懂 AI 写的代码**,至少理解它做了什么、有什么副作用。
- 对不理解的部分,直接问 AI「这段为什么这么写?」

### 步骤 7:重构与收敛

- 原型跑通后,让 AI 帮你:补充异常处理、加日志、加类型注解、加注释。
- 删除冗余、统一风格。

### 步骤 8:固化与提交

- 补充测试(哪怕是简单的验证脚本)。
- 写清晰的提交信息。
- 通过 Git 提交,形成可回滚的检查点。

## 六、提示词(Prompt)技巧

| 技巧 | 说明 | 示例 |
|------|------|------|
| **给上下文** | 说明环境、版本、已有代码 | 「Maya 2024,Python 3.11,优先用 pymel」 |
| **给约束** | 明确规范和限制 | 「函数必须带类型注解和 docstring」 |
| **给样例** | 提供输入/输出例子 | 「输入 ['joint1','joint2'],应生成 ctrl_joint1...」 |
| **分步要求** | 让 AI 先给计划再写码 | 「先列出实现步骤,我确认后再写代码」 |
| **要求自检** | 让 AI 指出风险 | 「指出这段代码可能出错的边界情况」 |
| **指定角色** | 设定专业视角 | 「以资深绑定 TA 的视角审查这段权重代码」 |
| **粘贴报错** | 原样给出错误信息 | 直接贴完整 traceback,而不是「报错了」 |

**反例(模糊提示)**:
> 「帮我写个绑定工具」

**正例(清晰提示)**:
> 「写一个 Python 函数(pymel),输入一个骨骼名称列表,为每个骨骼创建一个圆形 NURBS 控制器,控制器命名为 `ctrl_<骨骼名>`,并用 parentConstraint 约束骨骼。函数要带类型注解、docstring,并对找不到骨骼的情况做异常处理和日志输出。」

## 七、注意事项与风险控制

### 🛡️ 安全网

1. **永远用 Git**:每个可工作的版本都提交,方便随时回退。
2. **小步提交**:别攒一大堆改动一次提交,出问题难定位。
3. **隔离危险操作**:对会修改/删除文件、资产、数据的操作,先在副本或测试场景验证。

### 🔍 审阅与信任

4. **不要盲目信任**:AI 会「自信地犯错」(幻觉)。它说「修好了」不代表真修好了。
5. **以运行结果为准**:验证看真实输出,不看 AI 的口头保证。
6. **理解再合并**:不理解的代码不要合入主分支。看不懂就让 AI 解释。

### 🔐 安全与质量

7. **警惕安全隐患**:AI 可能引入硬编码密钥、SQL 注入、不安全的反序列化等。涉及安全的代码要专门审查。
8. **检查依赖**:AI 可能引入不必要或不存在的第三方库,核实后再用。
9. **注意性能**:对密集计算(顶点形变、批量资产)审查算法复杂度,必要时用更底层的 API(如 Maya API 2.0)。

### 📉 长期维护

10. **防止「代码债」堆积**:Vibe Coding 容易快速产出大量代码,要定期重构、补测试、写文档,否则维护成本会反噬。
11. **保持自己的能力**:别让 AI 完全代替思考。核心逻辑你要能独立看懂、能手动改。
12. **AI 不懂你的全局**:它只看到你给的上下文。架构级决策(模块划分、数据流)应由你主导。

## 八、技术美术 / DCC 脚本场景示例

结合 Maya / UE / MotionBuilder 的典型 Vibe Coding 用法:

### 场景 1:Maya 批量绑定脚本

```
意图:为选中的多个角色骨架批量创建 FK 控制器。
↓
让 AI 先处理单个骨架(最小可运行)。
↓
在 Maya 中运行,验证控制器层级、命名、约束正确。
↓
反馈:「再加上对每个角色的 try-except,单个失败不中断整体,并打印日志」。
↓
审阅:确认异常处理覆盖了「骨骼缺失」「重名」等情况。
```

> 对应规范:批量脚本务必加 try-except 和清晰日志,确保单个资产错误不中断整个流程。

### 场景 2:UE5 资产批处理

```
意图:批量给一批 SkeletalMesh 设置 LOD 与碰撞。
↓
让 AI 用最新的 unreal 模块,先写「处理一个资产」。
↓
在编辑器里跑,验证设置生效。
↓
迭代:加上进度反馈、批量遍历、异常捕获。
↓
审阅:确认操作的性能(避免逐个保存导致卡顿)。
```

### 场景 3:PySide 工具 UI

```
意图:做一个带进度条的批处理工具窗口。
↓
让 AI 先搭出空窗口 + 按钮(可运行)。
↓
逐步加:点击回调、QThread 后台执行、进度更新。
↓
注意:UI 线程安全,耗时操作放后台线程,避免界面卡死。
```

> DCC 工具开发特别注意:MotionBuilder 的内存泄漏与 UI 线程安全;Maya/MoBu 的 UI 与主线程交互。

## 九、常见反模式(Anti-patterns)

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| 「一句话写完整个系统」 | 产出庞大、难验证、难调试 | 拆成可独立验证的小步 |
| 不运行就相信 | AI 幻觉导致代码跑不通 | 每步必跑、看真实结果 |
| 不读 AI 写的代码 | 埋下看不懂的坑 | 至少读懂关键逻辑 |
| 不用版本控制 | 出错无法回滚 | 全程 Git,小步提交 |
| 报错只说「不行」 | AI 无法定位 | 贴完整报错信息 |
| 一次改一大片 | 引入新问题难排查 | 一次聚焦一个改动 |
| 把原型直接上生产 | 缺测试、缺安全审查 | 收敛、补测试、安全审阅后再上 |

## 十、检查清单(Checklist)

开始前:
- [ ] 已初始化 Git(有安全网)
- [ ] 有可快速运行验证的环境
- [ ] 项目规范已写入规则文件(命名、技术栈、语言)

迭代中:
- [ ] 意图描述清晰(目标 + 上下文 + 成功标准)
- [ ] 每步都是可独立验证的小颗粒
- [ ] 每次生成后**亲自运行**验证
- [ ] 报错信息原样反馈给 AI

合并前:
- [ ] 已读懂并理解关键代码
- [ ] 已补充异常处理、日志、类型注解、docstring
- [ ] 危险/不可逆操作已在副本验证
- [ ] 涉及安全/性能的部分已专门审查
- [ ] 已补充基本测试或验证脚本
- [ ] 已用清晰信息提交

## 结语

Vibe Coding 不是「让 AI 替你思考」,而是**把你从重复劳动中解放出来,专注于意图、判断和质量把控**。

> **AI 负责快,你负责对。**
> 用得好,它是放大器;用不好,它是放大错误的放大器。

保持掌控、小步迭代、运行验证、审阅理解 —— 这四点,是从「玩票式 Vibe Coding」走向「可靠的 AI 辅助开发」的关键。
