在 Autodesk Maya 中，**Dependency Graph**（依赖图）是 Maya 的核心架构之一，用于管理和组织场景中的节点及其之间的关系。它是 Maya 处理数据流和计算的基础，广泛应用于建模、动画、渲染等功能。以下是对 Dependency Graph、Dirty Propagation、Pull/Push 机制以及 Lazy Evaluation 的详细介绍：

---

### 1. Dependency Graph（依赖图）
Dependency Graph 是 Maya 中用于表示节点（Nodes）之间依赖关系的有向无环图（DAG，Directed Acyclic Graph）。它定义了场景中数据的流动和计算逻辑，分为两种主要类型：

- **DAG（Directed Acyclic Graph）**：主要用于场景的层次结构（如变换节点、网格等），处理对象的父子关系和空间变换。
- **DG（Dependency Graph）**：更广泛的概念，涵盖所有节点之间的数据依赖关系，包括非层次结构的数据流（如材质、动画曲线、表达式等）。

#### 核心概念
- **节点（Nodes）**：Dependency Graph 由各种节点组成，每个节点代表一个功能单元（如变换、几何体、材质、动画曲线等）。
- **属性（Attributes）**：节点包含输入和输出属性，数据通过这些属性在节点之间传递。
- **连接（Connections）**：节点之间的属性通过连接（Connections）关联，定义了数据流的路径。
- **有向无环**：数据流是有方向的，且不会形成循环，以确保计算的稳定性。

#### 工作原理
- 每个节点根据其输入属性计算输出属性。例如，一个变换节点的输出（世界矩阵）可能依赖于其平移、旋转、缩放的输入属性。
- 节点之间的连接形成一个网络，Maya 通过遍历这个网络来计算场景的最终状态（如渲染、动画更新等）。

---

### 2. Dirty Propagation（脏传播）
Dirty Propagation 是 Maya 用于跟踪和优化计算的一种机制，用于标记哪些节点需要重新计算。

#### 定义
- 当一个节点的输入属性发生变化时，该节点及其下游（依赖它的节点）会被标记为 **“脏”（Dirty）**，表示它们的输出可能不再有效，需要重新计算。
- 脏传播是 Dependency Graph 高效运行的关键，避免了对整个场景的无谓重新计算。

#### 工作流程
1. **属性变化**：某个节点的输入属性（如平移值）发生变化。
2. **标记脏状态**：Maya 将该节点标记为“脏”，并沿着 Dependency Graph 的连接向下游传播脏状态，标记所有受影响的节点。
3. **按需计算**：只有被标记为脏的节点会在下次求值时重新计算，未标记的节点则保持缓存结果。

#### 优化作用
- 通过只重新计算脏节点，Maya 避免了不必要的计算，特别是在复杂场景中。
- 例如，修改一个物体的位置只会导致其变换节点及其相关节点（如绑定蒙皮）变脏，而不影响无关的节点（如其他物体的材质）。
#### "Dirty" and "Clean"
##### 概述
- 一个节点被标记为 Dirty 表示其输出可能不再有效，需要在下次求值时重新计算。以下是导致节点被标记为 Dirty 的主要情况：
	1. 输入属性发生变化：当节点的某个 输入属性（Input Attribute）的值发生修改时，该节点会被标记为 Dirty。
	2.  上游节点变 Dirty：如果一个节点的 上游节点（即其输入依赖的节点）被标记为 Dirty，那么该节点也会被标记为 Dirty。这种传播机制称为 Dirty Propagation（脏传播）。
	3. 节点结构或连接发生变化：当 Dependency Graph 的结构发生变化时，相关节点会被标记为 Dirty。
	4. 动画时间变化：当场景的时间（Time）发生变化时，与时间相关的节点（如动画曲线、表达式）可能会因为时间依赖而变 Dirty。
	5. 外部影响或强制刷新：某些外部操作可能导致节点被标记为 Dirty，例如：
		1. 手动刷新场景（例如通过 Maya 的界面或脚本强制重新求值）。
		2. 某些插件或脚本显式地将节点标记为 Dirty。
- 一个节点被标记为 Clean 表示其输出是有效的，可以直接使用缓存的结果而无需重新计算。以下是节点被标记为 Clean 的主要情况：
	1. 节点完成求值： Dirty 节点被 Maya 的求值器（Evaluator）重新计算并生成有效的输出后，该节点会被标记为 Clean。
	2. 输入属性未发生变化：如果一个节点的输入属性没有变化，且其上游节点都是 Clean 的，那么该节点保持 Clean 状态。
	3. 缓存有效：Maya 的 Lazy Evaluation（延迟求值） 机制会检查节点的 Dirty 状态。如果节点是 Clean 的，且其缓存的输出仍然有效，Maya 会直接使用缓存结果，而不会重新计算。
	4. 场景重置或初始化：在某些情况下，Maya 可能会重置节点的 Dirty 状态，例如：
		1. 新建场景或加载场景时，Maya 会根据初始状态设置节点的 Clean/Dirty 状态。
		2. 某些全局刷新操作可能将所有节点标记为 Clean（如果没有变化需要计算）。
##### Dirty 和 Clean 的工作流程

以下是 Dirty 和 Clean 状态在 Dependency Graph 中的典型工作流程：

1. **初始状态**：场景中的节点在初始化时通常是 Clean 的（假设所有输出都有效）。
2. **触发 Dirty**：某个节点的输入属性发生变化（如用户修改、动画时间变化），该节点被标记为 Dirty。
3. **脏传播**：Dirty 状态通过 Push 机制传播到所有依赖该节点的节点。
4. **求值触发**：当需要节点的输出时（通过 Pull 机制，如视口刷新或渲染），Maya 检查 Dirty 状态：
    - 如果是 Dirty，重新计算并更新输出，之后标记为 Clean。
    - 如果是 Clean，直接使用缓存的输出。
5. **重复循环**：当再次发生变化时，重复上述过程。

---

### 3. Pull/Push Mechanism（拉/推机制）
Maya 的 Dependency Graph 使用 **Pull/Push 机制**来处理数据流和计算。这两种机制共同决定了节点如何响应数据请求和更新。

#### Pull（拉）机制
- **定义**：当 Maya 需要某个节点的输出属性值时，它会“拉”取该值。这会触发该节点的计算，并递归地拉取其输入属性的值。
- **工作方式**：
  - 例如，渲染器需要一个物体的世界矩阵，Maya 会从变换节点“拉”取输出。
  - 如果该节点的输入（如平移、旋转）是脏的，Maya 会递归地拉取上游节点的输出，直到所有依赖的数据都计算完成。
- **特点**：Pull 是一种按需计算的机制，只有在需要输出时才会触发计算，符合 Lazy Evaluation 的理念。

#### Push（推）机制
- **定义**：当一个节点的输入属性发生变化时，Maya 会“推”送脏状态到下游节点，通知它们需要重新计算。
- **工作方式**：
  - 例如，修改一个动画曲线的关键帧会使相关节点的输入属性变脏，Maya 会沿着 Dependency Graph 向下游推送脏标记。
  - 这些被标记为脏的节点会在下次被拉取时重新计算。
- **特点**：Push 机制确保了脏状态的正确传播，但实际计算通常延迟到 Pull 阶段。

#### Pull 和 Push 的协作
- **Push** 负责标记哪些节点需要更新（脏传播）。
- **Pull** 负责在需要时触发实际的计算。
- 这种组合确保了 Maya 仅在必要时执行计算，优化了性能。

---

### 4. Lazy Evaluation（延迟求值）
Lazy Evaluation 是 Maya Dependency Graph 的核心优化策略，旨在减少不必要的计算，提高性能。

#### 定义
- Lazy Evaluation 意味着 Maya 不会立即计算所有节点的输出，而是在需要某个节点的输出时才进行计算。
- 结合 Pull 机制，只有当某个节点的输出被请求时，Maya 才会遍历 Dependency Graph，计算脏节点及其依赖。

#### 工作原理
- **缓存机制**：如果一个节点的输入没有变化，其输出会被缓存，避免重复计算。
- **按需计算**：当某个输出被请求时，Maya 检查该节点是否为脏：
  - 如果是脏的，重新计算并更新缓存。
  - 如果不是脏的，直接返回缓存的结果。
- **脏传播的配合**：脏传播（Push 机制）确保只有受影响的节点被标记为脏，而 Lazy Evaluation 确保只有被拉取的脏节点才会被计算。

#### 优势
- **性能优化**：在复杂场景中，只有必要的节点被计算，避免了全局重新计算。
- **动态更新**：支持实时交互，如在视口中拖动物体时，仅更新相关的变换和几何数据。
- **扩展性**：Lazy Evaluation 使 Maya 能够处理大型场景，因为无关的节点不会占用计算资源。

#### 示例
- 假设一个场景包含一个带动画的立方体和一个静态球体：
  - 修改立方体的动画关键帧会导致其变换节点变脏。
  - 当视口需要渲染时，Maya 只重新计算立方体的变换及其相关节点（如蒙皮），而静态球体的节点保持缓存状态，不重新计算。

### 5. maya的求值模式（Evaluation Modes）

在 Autodesk Maya 中，**求值模式（Evaluation Modes）** 是指 Maya 的 **Dependency Graph (DG)** 求值器（Evaluator）用来计算节点和更新场景的方式。不同的求值模式决定了如何处理 Dependency Graph 中的节点计算，特别是在处理复杂场景、动画和交互时的性能和行为。Maya 提供了几种主要的求值模式，包括 **DG 模式**、**Serial 模式** 和 **Parallel 模式**，这些模式在计算效率、线程安全和实时交互方面各有特点。以下是对这些模式的详细介绍。

---

### 1. 概述：Maya 的求值机制
- **Dependency Graph (DG)**：Maya 的核心数据结构，由节点和它们的连接组成，负责处理场景中的数据流（如变换、动画、材质等）。
- **求值器（Evaluator）**：Maya 使用求值器遍历 Dependency Graph，计算节点的输出（如世界矩阵、几何位置等）。
- **Dirty Propagation 和 Lazy Evaluation**：求值器依赖脏传播（标记需要重新计算的节点）和延迟求值（仅在需要时计算），以优化性能。
- **求值模式的作用**：不同的求值模式决定了计算的顺序、并行性以及如何处理多线程，从而影响场景的性能和稳定性。

Maya 的求值模式可以通过界面（**Evaluation Toolkit** 或 **Preferences** 窗口）或 MEL/Python 脚本切换，常见模式包括 DG、Serial 和 Parallel。

---

### 2. DG 模式（Directed Graph Mode）
DG 模式是 Maya 的传统求值模式，也是最基础的模式，适用于大多数简单场景。

#### 特点
- **单线程计算**：DG 模式以单线程方式按需计算节点，严格按照 Dependency Graph 的拓扑顺序（从上游到下游）执行。
- **按需求值（Pull 机制）**：只有当某个节点的输出被请求（如视口刷新、渲染）时，Maya 才会计算该节点及其依赖的节点。
- **适合简单场景**：由于是单线程，DG 模式在简单场景中表现良好，但在复杂场景（大量节点、动画或绑定）中可能较慢。

#### 工作原理
- 当某个节点被标记为 Dirty（例如输入属性变化或时间变化），Maya 遍历 Dependency Graph，找到所有 Dirty 节点。
- 按依赖顺序逐一计算这些节点，更新它们的输出，并标记为 Clean。
- 如果某些节点不是 Dirty，Maya 直接使用缓存的输出（Lazy Evaluation）。

#### 优点
- **简单可靠**：逻辑清晰，适合调试和开发。
- **兼容性强**：支持所有 Maya 功能和插件，因为它是最早的求值模式。
- **低内存需求**：单线程计算不会占用过多资源。

#### 缺点
- **性能瓶颈**：在复杂场景中，单线程计算可能导致性能下降，尤其是涉及大量动画或绑定计算时。
- **无法利用多核处理器**：不适合现代多核 CPU 的性能优化。

#### 使用场景
- 小型场景或不需要高性能的实时交互。
- 调试 Dependency Graph 或插件时。
- 老旧工作流或需要最大兼容性的场景。

#### 设置方式
- 通过界面：**Windows > Settings/Preferences > Preferences > Animation > Evaluation**，选择 **DG**。
- 通过 MEL：`evalDeferred("optionVar -sv evaluationMode DG");`
- 通过 Python：`maya.cmds.optionVar(sv="evaluationMode", value="DG")`

---

### 3. Serial （串行）模式（Serial Evaluation Mode）
Serial 模式是 DG 模式的增强版本，仍然是单线程计算，但引入了更现代化的求值管理机制。

#### 特点
- **单线程，但优化调度**：Serial 模式仍然按顺序计算节点，但使用了更高效的 **Evaluation Manager**（求值管理器）来调度计算。
- **支持并行准备**：虽然计算本身是单线程的，Serial 模式可以为并行求值做准备（如构建求值图）。
- **改进脏传播**：相比 DG 模式，Serial 模式的脏传播和节点调度更高效，减少不必要的计算。

#### 工作原理
- **Evaluation Graph**：Serial 模式构建一个优化的求值图（Evaluation Graph），明确节点的计算顺序和依赖关系。
- **按需求值**：与 DG 模式类似，只有 Dirty 节点会被计算，但调度更智能。
- **时间驱动**：Serial 模式对动画时间的变化（例如时间轴移动）处理更高效，适合动画播放。

#### 优点
- **性能提升**：相比 DG 模式，Serial 模式的调度和脏传播更高效，特别是在动画播放或中等复杂度的场景中。
- **兼容性**：与 DG 模式一样，兼容大多数插件和功能。
- **过渡模式**：为 Parallel 模式提供了一个中间过渡，适合逐步迁移到多线程求值。

#### 缺点
- **仍为单线程**：无法充分利用多核 CPU 的性能。
- **复杂场景受限**：在极大规模的场景中，性能仍然可能不如 Parallel 模式。

#### 使用场景
- 中等复杂度的场景，需要比 DG 模式更好的性能但又不希望冒险使用 Parallel 模式。
- 测试或逐步迁移到 Parallel 模式时。

#### 设置方式
- 通过界面：**Windows > Settings/Preferences > Preferences > Animation > Evaluation**，选择 **Serial**。
- 通过 MEL：`evalDeferred("optionVar -sv evaluationMode Serial");`
- 通过 Python：`maya.cmds.optionVar(sv="evaluationMode", value="Serial")`

---

### 4. Parallel（并行） 模式（Parallel Evaluation Mode）
Parallel 模式是 Maya 引入的现代化求值模式，利用多核 CPU 进行并行计算，显著提升复杂场景的性能。

#### 特点
- **多线程计算**：Parallel 模式将 Dependency Graph 的节点分配到多个线程，允许同时计算多个独立节点。
- **动态调度**：使用 Evaluation Manager 动态分配任务，确保线程高效利用。
- **复杂场景优化**：专为大型场景、复杂动画和绑定设计，能够显著减少计算时间。

#### 工作原理
- **构建求值图**：Parallel 模式首先分析 Dependency Graph，构建一个优化后的求值图，识别可以并行计算的节点。
- **任务分割**：将 Dirty 节点的任务分配到多个线程，独立计算无依赖关系的节点。
- **同步机制**：确保线程之间不会发生冲突（例如，依赖同一上游节点的计算会等待上游完成）。
- **缓存和脏传播**：与 Serial 模式类似，依赖 Lazy Evaluation 和脏传播，仅计算必要的节点。

#### 优点
- **高性能**：充分利用多核 CPU，显著提升复杂场景的计算速度（如绑定、动画播放、模拟）。
- **实时交互**：在视口中拖动对象或播放动画时，Parallel 模式提供更流畅的体验。
- **现代化设计**：专为现代硬件和工作流优化。

#### 缺点
- **兼容性问题**：某些老旧插件或自定义节点可能不完全支持多线程，导致错误或崩溃。
- **调试复杂**：由于多线程的复杂性，调试 Dependency Graph 或节点问题可能更困难。
- **内存占用**：多线程可能增加内存使用，尤其在超大规模场景中。

#### 使用场景
- 大型场景，包含大量动画、绑定、模拟或粒子效果。
- 需要高性能实时交互的工作流（如动画制作、游戏资产开发）。
- 使用现代硬件（多核 CPU）的工作站。

#### 设置方式
- 通过界面：**Windows > Settings/Preferences > Preferences > Animation > Evaluation**，选择 **Parallel**。
- 通过 MEL：`evalDeferred("optionVar -sv evaluationMode Parallel");`
- 通过 Python：`maya.cmds.optionVar(sv="evaluationMode", value="Parallel")`

#### 注意事项
- **插件兼容性**：Parallel 模式要求插件支持多线程求值。如果插件未正确实现，可能导致不可预测的结果。可以通过 **Evaluation Toolkit** 检查插件兼容性。
- **安全模式**：Maya 提供了 **Safe Mode**，用于检测和隔离不安全的节点，防止崩溃。
- **GPU 覆盖**：Parallel 模式可以与 GPU 加速（如 GPU Override 模式）结合，进一步提升性能（例如，视口中的变形器计算）。

---

### 5. 三种模式的对比
| 特性                  | DG 模式                     | Serial 模式                 | Parallel 模式               |
|-----------------------|-----------------------------|-----------------------------|-----------------------------|
| **计算方式**          | 单线程，顺序计算            | 单线程，优化调度            | 多线程，并行计算            |
| **性能**              | 较低，适合简单场景          | 中等，适合中等复杂场景      | 最高，适合复杂场景          |
| **兼容性**            | 最高，兼容所有插件          | 高，兼容大多数插件          | 较低，部分插件可能不兼容    |
| **调度机制**          | 简单，按需求值              | 优化求值图，智能调度        | 动态任务分配，多线程调度    |
| **内存占用**          | 较低                        | 中等                        | 较高                        |
| **调试难度**          | 简单                        | 中等                        | 较高                        |
| **适用场景**          | 小型场景、调试              | 中等场景、过渡模式          | 大型场景、高性能需求        |

---

### 6. 其他相关概念
- **Evaluation Toolkit**：
  - Maya 提供了 **Evaluation Toolkit**（在 **Animation > Evaluation Toolkit** 菜单中），用于调试和优化求值模式。
  - 功能包括：
    - 检查节点的 Dirty 状态。
    - 分析求值性能（如哪些节点耗时最多）。
    - 检测 Parallel 模式的兼容性问题。
- **GPU 加速**：
  - 在 Parallel 模式下，Maya 支持将某些计算（如变形器）卸载到 GPU，进一步提升性能。
  - 启用方式：**Preferences > Animation > GPU Override**。
- **Custom Evaluators**：
  - 高级用户可以通过 Maya 的 API（C++ 或 Python）创建自定义求值器，扩展或修改求值行为。
- **Time-Driven Evaluation**：
  - 所有模式都支持时间驱动的求值（例如，动画曲线随时间变化），但 Parallel 模式对时间变化的处理更高效。

---

### 7. 实际例子
假设一个场景包含 100 个带动画的角色，每个角色有蒙皮和动画曲线：
- **DG 模式**：逐一计算每个角色的变换和蒙皮，可能导致视口卡顿。
- **Serial 模式**：优化调度后，计算速度略有提升，但仍受限于单线程。
- **Parallel 模式**：将不同角色的计算分配到多个线程，大幅提高视口刷新速度，适合实时预览。

---

### 8. 总结
- **DG 模式**：传统单线程模式，简单可靠，适合小型场景或调试，但性能较低。
- **Serial 模式**：单线程优化模式，调度更高效，适合中等场景或过渡到 Parallel 模式。
- **Parallel 模式**：多线程模式，性能最高，适合复杂场景，但需要注意插件兼容性。

# 节点ID

### **MTypeId 的分配规则**

为了防止不同的插件之间发生冲突，Autodesk 对 `MTypeId` 的使用范围进行了划分：

1. **Autodesk 预留范围: `0x0` - `0x7FFFF`**
    
    - 这个范围（十进制的 0 到 524287）是 Autodesk 为 Maya 内部自带的节点（如 `transform`, `mesh`, `lambert` 等）预留的。
        
    - **绝对不要** 在这个范围内选择ID。否则，当你的插件加载时，很可能会覆盖掉 Maya 的一个核心节点，导致程序崩溃或出现无法预料的错误。
        
2. **第三方开发者范围: `0x80000` - `0xFFFFFFF`**
    
    - 这个范围（十进制的 524288 以上）是专门留给第三方开发者（就像我们现在这样）使用的。
        
    - 你选择的 `0x87000` (十进制 552960) 正好处在这个安全的范围内，所以你的选择是**正确**的。
        

### **为什么说“通常”可用？（潜在的冲突风险）**

即使你选择了 `0x80000` 以上的ID，仍然存在一个非常小的风险：**ID冲突**。

想象一下，如果有另一个开发者（或者你自己写的另一个插件）也恰好选择了 `0x87000` 作为ID，那么当这两个插件同时在 Maya 中加载时，只有第一个加载的插件能成功注册该ID，后一个会失败并报错。

### **选择 ID 的最佳实践**

根据插件的用途，选择ID的策略也不同：

|插件用途|推荐策略|示例|
|---|---|---|
|**商业发布或团队共享**|**向 Autodesk 申请唯一的ID块**。这是最专业、最安全的方法，可以保证你的ID全球唯一。|Autodesk会分配给你一个专属范围，例如 `0x81000` 到 `0x810FF`。|
|**公司内部或个人项目**|选择一个看起来比较随机的、**数值较大**的ID。这样可以极大降低与网络上其他未注册插件冲突的概率。|`0x87F1A`, `0x9C44B`, `0x80123`|
|**学习和测试**|使用像 `0x87000` 这样简单好记的ID完全没问题。它清晰地表明这是一个自定义节点，并且处在正确的范围内。|`0x87000`, `0x80001`|

### **结论**

你选择的 `om.MTypeId(0x87000)` 是一个非常理想的ID，尤其适合学习和开发阶段。它遵循了 Autodesk 的规范，不会与 Maya 的内置节点冲突。

当你准备将插件用于更广泛的生产环境时，可以考虑选择一个更“奇特”的数字，以进一步降低与他人冲突的风险。
